# Module implementation map

This document maps the 22 additions in [MODULAR-MEMORY-PLAN.md](MODULAR-MEMORY-PLAN.md) to the current implementation. The plan remains the original design review; this map records what was built and where its limits remain. Test links identify concrete assertions in source. They do not, by themselves, establish that a suite passed against the final distribution. Preserve the actual run logs and candidate identity with the release evidence.

The implementation adds companion contracts, immutable packages and a separate workbench for the existing NFT/account. It does not replace an already minted collection, account, renderer or original runtime. An ordinary reviewed account action still advances the account's nonce and audit root. Its live activity artwork can therefore change as designed while the original seed, genome, proof state, source assets and runtime bindings remain unchanged.

## Recovery after a lost staged-state receipt

`stageState` can succeed before a module has ever been activated. Recovering only `modulesOf` would then omit its namespace. `TokenModuleRegistry.stateModuleCount(tokenId)` and `stateModulesOf(tokenId, cursor, limit)` now maintain an independent, duplicate-free, NFT-scoped catalog. Both staging and active writes index their namespace. Staging still changes neither the active installation catalog/history nor `rootOf`.

`recoverToken` reads the union of installed module keys and those state keys, then verifies every retained state record and its bytes. The SDK integration deliberately discards the staged receipt and recovers the never-activated namespace through the independent `--token` CLI. This closes the lost-receipt discovery gap without activating an unfinished migration or accepting an unverified state hash. A previously published registry lacking these functions cannot gain them through a client update; it requires the correct new companion anchor.

## HTML runtime and browser evidence

The original owned-cartridge launcher and the new workbench are different execution profiles. The original compatibility fixture uses unchanged wallet/launcher source and complete raw HTML. It does not grant that old host new capabilities.

The workbench's HTML path keeps HTML inert in the frame and moves recovered scripts into a worker. Its bridge supports `getElementById` or a single `#id` selector; bounded `textContent`, `value`, `checked` and `disabled`; and `click`, `input` and `change` events. Full DOM APIs, arbitrary frame navigation and unrestricted networking are outside this profile. Unsupported application code can fail; selecting an HTML archive does not certify that it will run under this subset. Typed scenes use trusted rendering code with validated data.

The [HTML host tests](../test/modules/host-html.test.mjs) exercise inert parsing, worker-script extraction, package-path restrictions, worker DOM messages, scoped form controls and shared dependency parts in source/harness fixtures. Source-level sandbox, handshake and cleanup assertions are not proof of CSP enforcement or browser scheduling. The actual-browser gate is `npm run test:modules:browser`; its final results must be recorded separately. This implementation map makes no claim that the final worker HTML or the complete already-minted Genesis runtime passed that gate.

## Deployment concurrency and remaining acceptance work

Archive deployment plans use ordinary CREATE address prediction. The factory's creation nonce is shared across its users. `validateDeploymentPlan` checks it before review, and `reconcileDeploymentJournal` checks it again before returning a remaining step. A conflicting transaction requires explicit reconciliation and a newly reviewed remaining plan. A check before signing is not an atomic reservation: intervening factory use can cause a later planned call to fail or produce a different address, which must be detected from its actual receipt/code before publication. Never edit a saved journal's success labels to manufacture completion.

No public deployment, funded testnet transaction, mainnet verification or independent security audit is established by this document. The [deployment guide](MODULES-DEPLOYMENT.md) describes the concrete plans and operational flow. Final acceptance still needs exact-candidate execution evidence, real browser/device coverage, practical RPC/gas/latency measurements, explicit passphrase backup/transfer handover where encrypted data is used, and review of existing system dependencies and account authorization modes. Journal encryption and local packet recovery are implemented; they do not make forgotten keys recoverable or erase plaintext a previous holder already knew.

The focused commands are `npm run test:modules`, `npm run test:modules:native` and `npm run test:modules:browser`. Native prerequisites and its direct-binary/compiler pins are documented in [test/modules/native/README.md](../test/modules/native/README.md). Test counts are not coverage percentages, and a successful local suite is not production certification.
