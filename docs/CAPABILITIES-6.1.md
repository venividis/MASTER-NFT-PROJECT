# ANIMA 6.1: capabilities and their actual execution paths

This source inventory follows `docs/ACTUAL-NFT-AUDIT.md`. That audit established that shielded launches and encrypted group chat already existed in the canonical NFT source while the hosted simulator omitted their routes. Edition 6.1 integrates those implementations into the primary interface and fixes the mismatch between visible controls and executable capabilities.

This document is an implementation inventory, not an independent security certification. No public Ethereum deployment, funded RAILGUN proof/broadcaster transaction, or physical-phone acceptance test is asserted here. A source implementation, a passing local transaction test, a deployed contract, and a correctly connected interface are separate milestones. Updating a website does not replace an already minted immutable application's bytes.

## Primary navigation

| What the owner opens | Actual route | What happens |
|---|---|---|
| Swap | `trade` → `v4` | The canonical v4 exchange prepares actual public or shielded execution. Private execution stops when its prerequisites are missing. |
| Launch | `launch` | The shared launch desk supports immediate v4 liquidity, configurable creator hooks, community sales, streaming auctions, fee claims, setup and the private wallet. |
| Vault | `vault` → `live` | The verified NFT account prepares real timed/cliff/linear lock operations. |
| Commons | `world` → `commons` | The dedicated encrypted conversation desk provides groups, invitation discovery, history, membership management, key rotation, identity recovery and verified setup. |
| Public rooms | `world-public` → `live` | Public WorldLedger messages and room administration use their existing live NFT-account route. Invitation-only posting does not conceal message contents. |
| Memory | `memory` | The interface distinguishes encrypted local notes, deliberately public inscriptions and the original nonrecoverable hash-only seal. |
| Launch link | `participant` | A chain-qualified community-sale or auction link opens participant terms, contributions/bids, settlement and available claims. |
| Atlas | `atlas` | Advanced contracts, games, identity, provider configuration and explicitly separated local economic rehearsals remain discoverable. |

The artwork carries no preview label. Its original identity remains fixed during navigation. A single camera explores the optical scene while the original turning controls remain in charge of turning. The old flat glow has an explicit depth continuation; the implementation does not claim that a two-dimensional image uniquely determines a three-dimensional interior. Function panels are independently readable and do not harvest private text into artwork effects.

## Privacy has distinct meanings

| Capability | Protection provided | Remaining public information or requirement |
|---|---|---|
| Encrypted group conversations | Browser-native P-256 ECDH, HKDF-SHA256 and AES-256-GCM; separately encrypted recipient epoch packages and padded messages | Wallet identities, membership, sender, timing, epoch/sequence and approximate size remain public. This is the existing custom protocol, not MLS, Double Ratchet or forward secrecy. |
| Group recovery | Passphrase-encrypted identity backups can reopen historical epochs addressed to that identity | Recipients can retain messages they previously decrypted. A compromised long-term recipient key can expose its historical key packages. NFT sale does not transfer keys or private history. |
| Private swaps | Configured RAILGUN inputs/outputs and supported cross-contract calls | Funded shielded balances, circuits, compatible deployments, synchronization, RPC/POI services and a broadcaster are required. Pool activity and external observations can reveal links. |
| Private launches | Supported ordinary and creator-hook launches can use shielded funding and return supported token, LP-share and refund outputs to a shielded recipient | Token identity, supply, pool, amounts, price, timing and public hook configuration remain visible. Local adapter tests do not verify an actual funded ZK proof/broadcaster transaction. |
| Private memory | Existing encrypted notebook and optional encrypted onchain handover | Public inscription is explicitly readable. Handover needs its separate deployed contracts and recipient consent. Old holders may retain content. |
| Screen concealment | Covers the screen or hides amounts visible to someone nearby | It does not encrypt transactions or messages. Locking cannot cancel a transaction already submitted. |

Encrypted chat requires only `PrivacyKeys` and `EpochGroupChat`; it does not require `PrivateMemoryHandover`. Setup can verify existing addresses against the edition's exact executable bytecode, or prepare deployment through the signing wallet. Immutable key-registry references are checked for consistency and correct binding. The private desk's entire subtree carries `data-private-surface` and renders decrypted content with `textContent`. Lock clears displayed messages, passphrases, selected backup files, epoch keys and pending private reviews. An unfinished file read or decryption cannot reopen the locked identity.

Conversation discovery is bounded and resumable directly from contract room state. Membership reconstruction uses the contract's public events and confirms every current member before preparing a rotation. An incomplete event scan fails rather than distributing an incomplete epoch. History is paginated and marks epochs that the loaded identity cannot authenticate or decrypt. Registering a replacement key is detected even when the room's membership-dirty flag remains false.

The manager is fixed in the current group contract. Group-manager migration and a forward-secure protocol upgrade require a separate reviewed design. These guarantees have not been invented or silently attributed to the existing encryption.

## Launch mechanisms and custody

| Mechanism | Funding and entitlement | Settlement and limits |
|---|---|---|
| Immediate v4 launch | A fixed-supply ERC20, chosen initial liquidity, actual pool and transferable redeemable LP shares. Compatible public actions can be funded by the signing wallet or verified NFT account. | Retained tokens are not automatically vested. LP shares are not permanently locked. Redemption includes principal and proportional earned LP fees. |
| Creator-hook v4 launch | Separate creator fees, configurable fee ownership/recipient, and optional recorded splitter claims | Future creator fees may be changed by the hook owner. Splits apply when funds are deposited. Current claims are in their actual accrued currencies; payout conversion and automatic reinvestment are not supplied. |
| Community sale | Native-currency contributions, capped raise and proportional participant token allocation | Before close, participants can withdraw. Below the minimum, they claim refunds. A successful settlement installs permanent liquidity in ANIMA's NativeMarket and creates the specified founder/treasury locks. This is not a Uniswap pool. |
| ANIMA streaming auction | Existing token inventory, released lots and funded standing limit bids | Sixty-four active bid slots; cancellation and pull claims; no minimum-raise guarantee and no automatic DEX migration. This is not official Uniswap CCA. |

NFT funding verifies the collection/account relationship, current owner, applicable custody epoch and account implementation before a compatible operation is reviewed. New retained tokens and LP shares can consequently belong to the NFT account rather than the signing EOA. Transferring the NFT changes its account authority and invalidates stale applicable reviews. The signing wallet remains responsible for the outer transaction signature and gas.

Conversations and participant pages use the signing wallet. They do not inherit the creator desk's NFT funding choice. The communication desk exposes that distinction explicitly when NFT funding is currently selected. Private wallet recovery keys remain independent of both funding routes.

Shareable links identify the network, mechanism contract and sale identifier. The participant can explicitly choose a read RPC to inspect verified public terms without connecting a wallet. Requests are visible to that provider. Contributions, bids and claims require a separate wallet connection, transaction review and signature. A link authenticates no promise of demand or financial return.

Pending transaction records preserve hashes and distinguish inclusion, confirmation, failure and unresolved replacement/reorganization states. A displayed successful simulation is not a completed transaction. Actual receipts and recovery determine the recorded outcome.

## Evidence and remaining setup

The focused communication checks execute the canonical `PrivacyKeys` and `EpochGroupChat` bytecode on local Ganache and use actual WebCrypto. They cover wallet-reviewed deployment, registration, invitations, consent, complete membership recovery, rotation, padded ciphertext, historical decryption, encrypted backup recovery, removed-member exclusion, invalid bytecode/immutable bindings and cancellation after locking. Real DOM checks cover private-surface isolation, text-only rendering, cleared passphrases, editing invalidation and late backup-file cancellation. The original privacy integration suite also exercises recipient-accepted NFT/memory handover, tampering rejection and authenticated local two-chain observations.

Other release checks cover compatible NFT-account transactions, launch mechanisms, shared participant links, private adapter integration, archive recovery and continuous navigation. The final release validation record is the authority for the complete passing-test count and exact archive/runtime hashes; this document does not carry forward an obsolete aggregate from an earlier edition.

For a public-chain product, the owner still needs the chosen compatible deployments and real funding. Communication additionally needs registered encryption identities. Shielded execution additionally needs its actual services, circuit access, synchronized funds and funded end-to-end proof/broadcaster verification. ENS entry needs the delegated parent and configured named-mint contracts. Autonomous scheduled exits require an operating funded executor. Shared worlds require the external server. These dependencies are not replaced by graphical controls.

The following complete catalog is mirrored in `web/instruments/capabilities.json` and `system-manifest.json`. “Configurable” means the source supplies an actual wallet/contract route whose listed dependencies must be satisfied. “Local model + source” means that a retained model and contract source exist; it does not assert a complete dedicated live screen for every action. “Research” means the function is not implemented.
