## NFT accounts, nesting, and agent identity

| Standard and current status | Actual specification boundary | What the master implements | What remains before claiming integration |
|---|---|---|---|
| [ERC-6551 — Review](https://eips.ethereum.org/EIPS/eip-6551) | A canonical permissionless registry, deterministic ERC-1167 accounts with immutable token data, account/signature interfaces, and an execution interface advertised through ERC-165. Accounts should use the singleton registry at `0x000000006551c19487814612e58FE06813775758`; the registry has a prescribed proxy format. | `contracts/src/core/SovereignAccount.sol` exposes `token`, `state`, `isValidSigner`, ERC-1271, token-controlled execution, epoch-bound sessions, and NFT custody. `SovereignAccountFactory.sol` deterministically deploys a complete custom account through CREATE2. | This is a custom token-controlled account with portions of the ERC-6551 interface. It does not use canonical registry addressing or the prescribed proxy. `supportsInterface` does not advertise an execution interface. Add a separately reviewed canonical-registry-compatible implementation if that interoperability is required; do not silently change existing account addresses. The optional execution interface is not the only permitted interface. |
| [ERC-7401 — Final](https://eips.ethereum.org/EIPS/eip-7401) | Parent-governed nesting distinguishes immediate parent ownership from root ownership, maintains proposed and accepted children, and defines acceptance, rejection, child transfers, and nested transfers. Ownership cycles require careful handling. It supersedes ERC-6059. | The account receives external ERC-721/ERC-1155 assets. Same-root-collection safe receipt is explicitly rejected. `web/confluence/console-core.mjs` defines a cartridge manifest and a local game runtime. | Custody and cartridge loading do not implement parent-governed nesting. No ERC-7401 child-management interface was found in the reviewed master. A nesting implementation needs direct/root ownership, approvals, pending/active children, transfer invalidation, bounded traversal, and cycle tests. A cartridge’s code execution permissions remain a separate concern. |
| [ERC-8004 — Draft](https://eips.ethereum.org/EIPS/eip-8004) | Identity registration, reputation feedback, and validation are separate registry functions. Identity points to registration metadata. Agent-wallet changes require proof; wallet metadata is cleared on identity transfer. Payment is orthogonal to the standard. | `contracts/src/core/IDontFuckingBelieveIt.sol::bindERC8004` stores a nonzero registry, agent ID, and proof hash once, with metadata and events. | Binding currently makes no registry call to verify identity ownership, wallet proof, or agent control. It is an external identity reference, not a verified registration or full registry implementation. Verify the deployed registry and identity relationship, implement explicit updates after transfers, and separately integrate any reputation/validation reads. A recorded proof hash does not prove an agent is trustworthy or functional. |

ERC-6551 also discusses asset removal before sale and ownership cycles. A marketplace must preview the actual account holdings and relevant state at transaction time; the NFT image is not a guarantee that its account still contains previously advertised assets. The master’s same-collection receiver check does not certify unsafe ERC-721 transfer paths. [ERC-6551 security considerations](https://eips.ethereum.org/EIPS/eip-6551#security-considerations)

## Onchain archives and web3://

[ERC-4804 is Final](https://eips.ethereum.org/EIPS/eip-4804). It translates web3 URLs into EVM **read calls**, with auto/manual resolution modes. It does not itself submit transactions, authorize spending, run browser code onchain, or supply content availability guarantees beyond the chosen chain/RPC/client.

[ERC-6860 is Draft](https://eips.ethereum.org/EIPS/eip-6860). It updates and clarifies this behavior. Missing or reverting `resolveMode()` defaults to auto mode. Manual mode passes path/query bytes as calldata and decodes returned ABI bytes; an empty path becomes `/`. Auto mode encodes method calls. The default return is ABI-encoded `bytes`; `returns=(bytes)` instead produces a JSON representation of decoded bytes and should not be used as a promise of HTML rendering. MIME behavior depends on mode and path; an arbitrary contract `mimeType` getter is not automatically consulted.

`contracts/src/protocol/OnchainApp.sol` stores an immutable, SHA-256-checked archive across STOP-prefixed code chunks and exposes `readChunk`/`readAll`. This is implemented source for onchain byte storage. It has no manual resolver, raw-path fallback, index route, asset routing, or web3 client integration. A web3 auto-mode client can potentially call `readAll`, but that does not establish a working website at its bare address. Browser execution of the recovered HTML, Wasm, and shader code remains offchain.

For a served archive, add and test a resolver adapter using the selected specification version and an actual web3 client: `/`, a nested asset, a missing asset, MIME selection, relative URLs, binary bytes, and chain/name resolution. Keep the archived content hash and deployed chunk addresses in the release manifest. Do not present an undeployed archive or an ordinary HTTPS preview as live web3 hosting.

## Uniswap v4 economics

| Boundary | Official behavior | Master source mapping |
|---|---|---|
| Hooks | A pool has one hook address chosen at initialization; a hook may serve multiple pools. Callbacks and return-delta permissions are encoded in the lowest 14 address bits, so a proposed hook address must satisfy its exact permission mask. [Hook concepts](https://developers.uniswap.org/docs/protocols/v4/concepts/hooks), [Hooks.sol](https://github.com/Uniswap/v4-core/blob/main/src/libraries/Hooks.sol) | Existing `contracts/src/kingdom/PhoenixLaunchHook.sol` checks its address permissions and manager-only callbacks. New `contracts/src/confluence/fees/OwnerLaunchFactory.sol` records a selected hook and pool-configuration hash only. It does not deploy that hook, initialize a pool, or add liquidity. |
| Dynamic LP fees | Dynamic status is selected when creating the pool. Its hook may update the stored LP fee or return a per-swap override. Dynamic fee flag is `0x800000`; override flag is `0x400000`; maximum LP fee is `1_000_000`, expressed in millionths (`3_000` = 0.3%). Only the pool’s hook may update its dynamic fee. [Dynamic fees](https://developers.uniswap.org/docs/protocols/v4/concepts/dynamic-fees), [LPFeeLibrary.sol](https://github.com/Uniswap/v4-core/blob/main/src/libraries/LPFeeLibrary.sol), [PoolManager.sol](https://github.com/Uniswap/v4-core/blob/main/src/PoolManager.sol) | Phoenix implements a fixed one-day LP fee ramp from 1% to 0.3%, with zero custom hook deltas. It is not an owner-authored fee policy or distribution engine. Changing the LP fee alone does not create arbitrary recipient payments. |
| Custom accounting and settlement | Hook-returned deltas can augment or bypass concentrated-liquidity accounting. Hook-earned fees can be distributed by hook logic to arbitrary recipients. Every nonzero currency delta must be settled before the PoolManager unlock returns. These capabilities require implemented accounting and permissions; they are not enabled by metadata. [v4 whitepaper §§2.2, 5](https://app.uniswap.org/whitepaper-v4.pdf), [Flash accounting](https://developers.uniswap.org/docs/protocols/v4/concepts/flash-accounting), [PoolManager.sol](https://github.com/Uniswap/v4-core/blob/main/src/PoolManager.sol) | `OwnerFeeRouter.sol` is a standalone router, explicitly not a hook. It attributes deposited native/ERC-20 assets to independently withdrawable claims and preserves earned claims across configuration changes. No v4 swap-to-router fee capture is implemented by this contract alone. |
| Output assets and LP rewards | A pool’s currencies bound its native swap/delta accounting. A donation accrues either or both pool currencies to in-range liquidity. Paying a different token requires an explicit conversion or separate funded distribution mechanism. [v4 whitepaper](https://app.uniswap.org/whitepaper-v4.pdf) | The router permits owner-allowlisted converters and beneficiary-chosen output with minimum-output and deadline constraints. Converter interfaces do not establish liquidity, pricing, or a deployed route. Frontend route planning in `web/confluence/economy.mjs` remains a plan until a configured transaction executes and its receipt is verified. |

For a real owner-selected v4 launch, implement the chosen hook policy, mine/verify its permission-compatible address, select the target chain’s official PoolManager, initialize the committed pool, provide liquidity, and connect fee capture to the router. Test exact-input/output swaps, both directions, zero/maximum fees, hook deltas, settlement, rounding, configuration changes, withdrawals, malicious callbacks, and failed conversions. A launch receipt should identify deployed token, hook, manager, pool ID, and actual initialized state rather than infer these from a commitment event.

## Accurate product labels at this snapshot

- **Implemented source:** deterministic individual appearance with a shared capability list; token-controlled accounts; external collectible custody; immutable archive storage; fixed-supply token creation; owner-defined deposit allocation; constrained converter interfaces; local cartridge/game execution.
- **Partial or referenced:** ERC-6551 interoperability; ERC-8004 identity binding; owner-selected pool configuration; web3 archive access.
- **Not established:** ERC-7401 nesting; canonical-registry accounts; verified ERC-8004 registration/validation; a served web3 site; configurable v4 fee capture and pool initialization; a live conversion venue; deployment addresses or successful onchain execution for this master release.

Official sources were read live; no secondary articles are used here. Source presence is distinct from compilation, tests, security review, deployment, and successful execution. The repository audit and upstream CI evidence are separately recorded in `research/github/GITHUB_SOURCE_AUDIT.md`.
