# Private extensions: memory, group chat and authenticated state

This release builds F02, F04 and F05 as callable contracts, a browser WebCrypto client and a private-data-aware workbench. The integration test uses the real ANIMA collection and SovereignAccount for minting, approval, transfer and custody-epoch checks. Cross-chain delivery is exercised on two local EVM chains using an explicitly named endpoint fixture.

| --- | --- | --- |
| F02 | Encrypt agent memory; store ciphertext and a salted content commitment onchain; encrypt a recipient-specific handover; recipient decrypts, verifies and accepts; atomic NFT transfer; cancellation, expiry and stale-custody protection. | Recipient-confirmed handover. No ZK/TEE proof of re-encryption, ERC-7857 compliance claim, seller erasure guarantee or automatic delivery through an ordinary NFT transfer. |
| F04 | Source snapshot queue; block-confirmation delay; custody recheck; LayerZero V2 wire-ABI dispatch/receive; immutable endpoint, peer, endpoint ID and EVM chain/collection domain; monotonic sequence and GUID replay protection; expiring remote observation; optional existing witness registry integration. | Read-only observations. No copied account authority, cross-chain asset minting or current-owner claim after source dispatch. Public endpoint/DVN activation and funded delivery are external deployment steps. |
| F05 | Wallet-authenticated encryption keys; room creation; expiring invitations and recipient consent; removal/leave; posting paused on membership/key changes; complete per-member epoch-key distribution; encrypted message storage/transport; message replay rejection; encrypted identity backup and historical package recovery. | Custom small-group protocol, maximum 32 members. ## Private agent memory

The owner first registers a P-256 encryption public key from their wallet. The private key remains in browser memory and can be exported only through the provided passphrase-encrypted backup flow. The owner encrypts memory to their own key and publishes the ciphertext alongside a SHA-256 commitment over a protocol domain, a random 32-byte salt and the exact UTF-8 memory. The salt stays inside encryption, preventing the public commitment from acting as an easy dictionary lookup of a short memory.

To offer a handover, the browser decrypts the owner's published memory and checks its commitment. It reads the recipient's wallet-registered public key, creates a random one-time receipt secret and encrypts the memory, salt and receipt secret to the recipient. Authenticated encryption binds the chain, contract, token, seller, recipient, custody epoch, memory version, recipient key generation, expiry, commitment and receipt hash.

The recipient's browser fetches the actual onchain envelope, decrypts it, checks the memory against the committed content, and verifies the receipt secret. Only then does the SDK return an unsigned acceptance transaction. The contract checks the recipient, receipt hash, memory version, current owner, current custody epoch, recipient key generation and expiry. The seller must have approved this handover contract for the NFT. Acceptance consumes the offer and transfers the NFT in one transaction. A failed transfer reverts acceptance. An offer cannot survive a transfer away and back because the account custody epoch changed.

The receipt is a random secret, not the plaintext memory or its salt. Publishing it during acceptance does not reveal the memory. It demonstrates possession of the receipt; it does **not** make the contract a mathematical verifier of decryption. A modified client can knowingly accept bad delivery if the recipient obtains the secret through another channel. The supplied client refuses substituted plaintext and tampered ciphertext. The seller can retain old memory, keys and the offered data. The buyer should create a fresh key and freshly encrypted memory for future updates. The separate `readReceivedMemory` / “Recover received memory” flow can decrypt the stored handover after acceptance using the appropriate backed-up key, without preparing another transfer.

[ERC-7857](https://eips.ethereum.org/EIPS/eip-7857) defines a separate ownership/transfer verification system, including TEE or ZKP-based proof paths. This extension deliberately identifies its different trust model: recipient verification and consent, with no claim that a receipt replaces that verification standard. Integrating a specific audited ERC-7857 prover/verifier would be another protocol edition, rather than relabeling this contract.

## Group encryption

Each room has a manager, a member list and an epoch. Membership is held by the consenting wallet; buying its NFT never silently grants its chat keys or historical identity. Invitation alone does not add a member. Acceptance, removal or leaving marks the room dirty and stops further posting. A registered key replacement also stops posting by every member until the manager rotates the epoch.

Rotation generates a new random 256-bit group key. The browser encrypts a separate key package to every current member's registered P-256 public key. The contract requires a sorted list containing exactly the current member count, rejects duplicates and nonmembers, checks each key generation, and stores all encrypted packages. Each member verifies the decrypted key against the onchain epoch commitment. A removed member receives no future package. Retaining the old key does not decrypt new messages produced by the supplied rotation client.

Message encryption binds chain, chat contract, room, epoch, sender and sequence. The wallet-authenticated transaction identifies the sender; the contract checks membership, epoch, key generations and expected sequence. Replay or reordered messages using a previously consumed sequence fail. The browser pads private message content to 256-byte increments before encryption to reduce exact length leakage. Addresses, room membership, ciphertext sizes, timing and activity remain public. Contract callers can deliberately submit arbitrary bytes; the supported client always encrypts before preparing a message transaction.

The manager is trusted to generate fresh keys and provide the correct key packages. The contract cannot prove randomness or prevent a member from sharing a key. Compromise of a long-term encryption private key can expose historical key packages encrypted to it, so this protocol does not claim forward secrecy. A clean new identity plus new membership epoch is needed after suspected key compromise. The protocol supports 32 members and does not attempt the tree-based scalability of MLS.

[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.txt) specifies MLS, including a ratchet tree, protocol key schedule, credentials and authenticated membership changes. We use the concept of membership epochs but implement a separately named, smaller protocol through native WebCrypto. We do not claim MLS wire compatibility, certification, forward secrecy or its post-compromise guarantees.

## Cryptographic envelope and recovery

- Native WebCrypto P-256 ECDH with a fresh ephemeral sender key for each envelope.
- HKDF-SHA256, a random 32-byte salt and explicit protocol-context information derive the AES-256 key.
- AES-GCM uses a random 96-bit IV and a 128-bit authentication tag. Domain/context is additional authenticated data.
- The envelope is `version || ephemeral SEC1 public key || salt || IV || ciphertext-and-tag`.
- Group messages derive a context-specific AES key from the epoch key and use a fresh random IV.
- Backups use PBKDF2-SHA256 with 600,000 iterations, a random salt, AES-256-GCM and a passphrase of at least 16 characters. The encrypted backup binds its public key as authenticated data. Wrong passphrases and public-key substitution fail.

Private keys and epoch keys are kept in memory by the supplied SDK. The workbench does not store plaintext, passwords or keys in local storage, logs, public-room methods or a generic onchain form. Lock clears references and attempts to zero mutable key arrays; JavaScript garbage collection is not a guaranteed secure-erasure mechanism. Backup recovery allows re-fetching old encrypted epoch packages, including historical messages for which that identity received a package. Losing the private key and backup loses decryption access. After replacing the registered public key, an old encrypted backup can still read its own historical key packages; current posting requires the currently registered key and current membership, so restoring an old backup does not restore old posting authority.

## Authenticated portal

`AuthenticatedStatePortal` uses the LayerZero V2 tuple layouts for `quote`, `send`, `allowInitializePath`, `nextNonce` and `lzReceive`, checked against the [official endpoint interface](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/protocol/contracts/interfaces/ILayerZeroEndpointV2.sol) (retrieved blob `ab6f5665239d6fde72400694ece8b2b04341a723`) and [receiver interface](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/protocol/contracts/interfaces/ILayerZeroReceiver.sol). The [LayerZero documentation](https://docs.layerzero.network/) is the deployment reference. The local fixture tests the exact tuple ABI and application checks; it is not represented as a DVN or public-chain consensus verifier.

Before any queue, dispatch or receipt is enabled, the deployer calls `configureTransport` with registered send/receive libraries, explicit ABI-encoded ULN confirmations and DVN sets, and a nonzero executor/max-message-size configuration. The contract calls the official endpoint setup methods itself. No mutable delegate is appointed. Both ULN directions require at least one explicit required DVN and non-default confirmations; optional DVNs must be explicitly supplied or explicitly disabled using the official `255` sentinel. The configured libraries and effective config hashes are checked immediately. `sealTransport` then irreversibly disables configuration. Each queue, dispatch and receipt rechecks the effective endpoint libraries/configuration and refuses drift or fallback to defaults. Setup uses the [official IMessageLibManager interface](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/protocol/contracts/interfaces/IMessageLibManager.sol) and [ULN configuration format](https://github.com/LayerZero-Labs/LayerZero-v2/blob/main/packages/layerzero-v2/evm/messagelib/contracts/uln/UlnBase.sol), retrieved from their primary repository.

The source owner queues a Bound account snapshot for up to one hour. Dispatch waits the configured number of source blocks and rejects an expired queue, missing source block hash, or any changed owner/custody epoch. A block-depth delay alone is not a consensus-finality proof. Public delivery additionally relies on the deployed endpoint and its pinned send/receive libraries and verification network.

The receiver accepts calls only from its immutable endpoint, for its immutable peer and source endpoint ID. It checks the source EVM chain and collection, replay GUID, transport nonce, per-token sequence, nondecreasing custody epoch and expiry. Accepted snapshots may be written into the existing `OmnichainWitnessRegistry` after the deployment owner sets this portal as adapter and freezes the registry.

An observation is a historical state, including historical ownership at source dispatch. Its `fresh` flag only means its expiry time has not passed. A source transfer occurring after dispatch cannot synchronously invalidate an in-flight message on another chain. No action in this portal can execute a wallet call, move remote account funds, create a second NFT purse or delegate authority from the observation.

Public deployment requires real source/destination endpoints, verified endpoint IDs and EVM chain IDs, deterministic peer deployment addresses, reviewed endpoint security configuration, executor options/fees, registry adapter setup where used, and a real funded delivery on both chains. Constructor bindings cannot later be changed. The present automated test uses two Ganache chains and a deliberately named `PrivacyEndpointFixture` relay.

## User and developer entry points

`web/extensions/privacy/desk.mjs` exports `mountPrivacyDesk(container, config)`. It accepts `config.contract(name)` for connected ethers-compatible contracts, `config.identity` with chain/owner/token, and `config.review` for unsigned transaction review. Plaintext and passphrases remain inside this panel. The review callback receives only contract transaction fields, public descriptions, ciphertext, salted commitments or the random acceptance receipt.

`web/extensions/privacy.mjs` exports `PrivacyClient` methods for identity creation/backup/restore, publication, ownership approval, handover proposal/decryption/acceptance preparation/cancellation, group creation/invitation/join/removal/leave/rotation/post/read, portal queue/quoted dispatch, and locking. Methods return unsigned transactions. Read methods fetch actual ciphertext from deployed contracts. It also exports `ACTIONS` containing public portal configure, seal and queue forms; dispatch quotes fees inside the private workbench. The secret-aware flow must not be replaced with generic text-to-calldata forms. The mount supports an optional `AbortSignal`; destruction/aborting cancels later transaction review and private data rendering, and key revision checks reject in-flight identity restoration after locking.

Run `node --test test/extensions/privacy.integration.test.mjs` after compiling the existing ANIMA core. The isolated helper compiles these new privacy contracts without overwriting shared build artifacts. Five cases cover real NFT handover/epoch invalidation, substituted and tampered memory, group consent/replay/removal/recovery/key replacement, in-flight operation cancellation after lock, and two-chain endpoint/domain authentication plus replay/custody/expiry rejection. Portal tests also cover pre-seal denial, sealed configuration immutability and endpoint-library drift rejection.
